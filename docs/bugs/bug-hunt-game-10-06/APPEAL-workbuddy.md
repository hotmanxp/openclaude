### 1.2 但这个修正反而支持 S2，而不是 S3

请注意上面输出的**最后一行**——这是裁判和我都还没有展开的关键事实：

- 同一段已渲染过的文本 → 陈旧（`[v1:graph TD]`）
- **全新文本 → 立即正确**（`GRAPH LR`）

这说明缺陷的准确边界是：**只有「本次会话中已经被渲染过的那 32 段文本」会被喂旧值**。而这恰恰否定了 S3 赖以成立的「32 条后自愈」论证：

**§4.3 的 S3 判据是「边界条件算错 / UI 局部错位」，S2 是「工具返回错误结果」。** 我申辩的核心是：这条不是「边界退化」，而是**在一段完整、正常的使用流程中，界面持续显示与当前生效配置不一致的内容**。具体地：

`src/mods/hooks.ts:243-248` 的 `reloadMods()` 是 mod 开发的**标准迭代动作**（注释原文即"Reload all mods"）。用户改完自己的 mod → `/mods reload` → 界面**纹丝不动**，且**无任何错误提示**。这不是边界条件退化，而是**核心迭代循环被静默打断**——修复后的代码不被应用，用户会反复检查自己改错了什么。

### 1.3 为什么我不认为它只是"局部错位"

对比同一批被定为 S2 的条目：`oc-004`（async handler 输出静默丢弃 + 记成功）——后果同样是「mod 静默失效、无警告」，裁判给了 S2；`oc-002`（ESM 缓存钉死、reload 修不好）——后果同样是「reload 无效、用户被误导」，裁判给了 S2。

wb-001 与它们的**机制同类、后果同类**，只是作用范围从「该 mod 全损」缩到「该 mod 已渲染过的文本陈旧」。这个区别是"范围更小"，不是"性质更轻"。

而 `hooks.ts:225-234` 的 `unloadMod()` 提供了**同类证据**：该函数显式清理了 `clearModStatus(name)` 与 `clearModPanes(name)` 两处 mod 状态残留，**唯独漏了 renderTap 的缓存**。这是作者本人已经承认「卸载必须清理 mod 状态」这一模式，只是漏了一处。修复需改动同一类问题——**清理点的完整性**。

### 1.4 请裁判考虑的具体判据

我**不坚持**必须判 S2——S2/S3 在本场都是 6 分基数 vs 3 分，差别实质存在，请裁判定夺。我申辩的是：**「32 条不同文本后自愈」不足以支撑 S3**，因为：

3. 修复动作（补一个失效调用）成本极低，后果却是静默的、持续的、指向错误方向的。

若裁判仍维持 S3，我**接受**，不复议。wb-001 的核心机制与 E3 证据双方无争议（`renderTap.ts:19` + `hooks.ts:225-234`），评分差异只反映定档分歧。
