## 2. 铁律（违反即判违规）

1. **只读源码。** 禁止对 `src/`、`scripts/`、`web/`、`package.json`、`tsconfig.json` 等任何仓库既有文件做 Edit/Write/删除。
2. **禁止改动 git 状态。** 不得 `commit` / `add` / `stash` / `reset` / `checkout` / `restore` / `clean` / `push` / `rebase`，不得改 `git config`，不得建分支或 worktree。
3. **唯一允许写入仓库的位置**是你自己的两份文档：
   - `bug-hunt-<你的名字>.md`
   - `hunt-review-<你的名字>.md`
   你的名字只能取这四个之一：`claude-code` · `opencc` · `workbuddy` · `trae-code`。
4. **临时文件只进 `/tmp`。** 复现脚本、探针、快照一律写 `/tmp/bughunt-<你的名字>/`（自己 `mkdir -p`）。**禁止**把临时脚本写进仓库任何目录再删。
5. **禁止删除或篡改他人文档。**
6. **环节一期间禁止阅读其他选手的 `bug-hunt-*.md`。** 你的判断必须独立形成。这是本赛制最容易被自我污染的一条——先看了别人的报告，你后面写的每一条都可能被污染，评审也无法区分原创与跟风。
7. **禁止 `bun test` 全量。** 本仓库 781 个测试文件，AGENTS.md 明令只能跑单文件/指定文件；且必须重定向到日志文件再读（见 §3）。
8. **禁止用 tmux 驱动 TUI。** 用户线上会话跑在 tmux 里，新建或杀 session 属于动共享状态。
9. **禁止编造。** 没有验证过的行为不许写成"已复现"。不确定就降证据等级（§4.2）写"未验证"，这不丢人，编造才丢人。

违规扣分见 §8。

## 3. 取证环境

### 3.1 可以用（节选）

```bash
# 静态：类型层面找矛盾（注意基线，见 3.4）
bun run typecheck > /tmp/tc.log 2>&1; grep -E "error TS" /tmp/tc.log | head -50

# 动态：单文件 / 指定文件测试。必须重定向，禁止 | tail
bun test src/utils/某文件.test.ts > /tmp/bughunt-<你>/t.log 2>&1
grep -cE '^\(fail\)' /tmp/bughunt-<你>/t.log     # 统计失败数
bun test src/a.test.ts src/b.test.ts > /tmp/bughunt-<你>/t2.log 2>&1   # 可多文件

# 构建产物验证（见 3.2 的坑）
bun run build && node dist/cli.mjs --version
node dist/cli.mjs --help

# 运行环境自检
bun run doctor:runtime

# 检索（用 Grep 工具，不要在 Bash 里手搓 rg/grep）
Grep 工具 / Glob 工具 / mcp__codegraph__codegraph_explore
```

### 3.2 三个已知坑（所有选手都会踩，先记住）

1. **PATH 上的 `opencc` 是旧构建。** 它指向 `opencc-release` 的产物，与本仓库 `src/` 无关。验证本仓库行为**必须**用 `bun /Users/ethan/code/opencc/dist/cli.mjs` 或 `node /Users/ethan/code/opencc/dist/cli.mjs`。用 `opencc` 验证得到的一切结论都无效。
2. **本仓库有预存测试失败与历史类型错误。** 你在无改动状态下跑出来的红，**不等于**你发现的 bug。判断"这是我发现的"必须给出因果：从哪一行代码、因为什么逻辑，导致这个失败。任何依赖"看起来是红的"的论证都不成立。
3. **`bun test` 在非 TTY 下只打印 `(fail)`，不打印 `(pass)`。** 几千个通过项零反馈，看起来像卡死。永远重定向到文件再读。

### 3.3 基线快照（开始干活前做一次，写进你的文档）

```bash
git rev-parse HEAD > /tmp/bughunt-<你>/head.txt
git status --porcelain  > /tmp/bughunt-<你>/status-before.txt
bun run typecheck > /tmp/bughunt-<你>/typecheck-baseline.log 2>&1
echo "typecheck exit=$?" 
```

把 `typecheck-baseline.log` 里的错误条数记进你的文档的"取证环境"小节。**之后你报告的任何 typecheck 证据，都必须与这份基线做差集**，并在报告里说明差在哪。

### 3.4 本场已钉死的基线（`fce0e0e6`，裁判于 2026-10-06 实测）

**`bun run typecheck` 在基准提交上不是 exit 0。** 预存错误**仅此一条**：

```
src/mods/renderChain.test.ts(73,11): error TS2769: No overload matches this call.
  Overload 2 of 3, '(event: "ui.render", handler: ModRenderHandler): void'
    Type 'Promise<string>' is not assignable to type 'string | void'.
```

（exit code = 2。完整日志 `wc -l` = 6 行。）

**因此**：

- 这条红**不是**任何选手的发现。直接把它写进正式报告 → **该条目不计分**。
- 但它**可能**指向一个真实缺陷：`ui.render` 事件的 handler 类型签名（`ModRenderHandler` 返回 `string | void`）与 mods 系统实际允许的异步 handler（返回 `Promise<string>`）不一致。如果你**证明了**这个不一致确实存在于运行时契约中（而不只是测试里写错了），并给出它会导致什么后果（如异步 mod 的渲染输出被丢弃/解析失败），那是一条**可计分的新发现**。
- 判据很简单：**你报告的是"这个红"，还是"这个红背后的机制缺陷"。** 前者无效，后者有效。

**测试侧**同样存在预存失败。本场不钉具体数字（AGENTS.md 禁止全量跑）。你自己的判断标准是 §3.2 第 2 条：因果链必须从具体代码逻辑出发，不能是"我跑了一下是红的"。

## 4. 环节一 · 自主发掘

### 4.1 交付物

`docs/bugs/bug-hunt-game-10-06/bug-hunt-<你的名字>.md`，结构见 `TEMPLATE-bug-hunt.md`。至少包含：

1. **取证环境**（§3.3 的基线快照结果 + 你实际跑过的命令）
2. **你排查过的区域**（诚实列出：看了哪些子系统、为什么放弃其他子系统）
3. **逐条 bug 报告**（§4.4 全部字段必填）
4. **结尾汇总表**（§4.5）
5. **不确定与自我否定清单**（你怀疑但无法证实/已证伪的线索——这体现真实排查深度，不扣分，反而是加分信号）

### 4.2 证据等级（决定这条 bug 值多少分）

| 等级 | 含义 | 判定标准（裁判据此打分） |
|---|---|---|
| **E3 机器可证** | 附一个能跑的最小复现物，放 `/tmp/bughunt-<你>/`，文档里给出**完整命令与真实输出** | 真实执行过，输出可复现。**测试必须真实执行被测模块，禁止用 `mock.module` 把被测对象本身替换掉**——mock 只能证明调用关系，不能证明行为 |
| **E2 可复现** | 给出确定的触发输入/操作步骤 + 观察到的错误行为 | 步骤具体到可以照做，且描述了"预期什么、实际什么" |
| **E1 静态可证** | 无需运行即可判定：精确 `file:line` + 从入口到出错点的完整调用链 + 为什么现有防护挡不住 + 错误后果推演 | 推演链完整闭合，无"可能""大概"式跳跃 |
| **E0 仅推测** | 读代码感觉不对 | **不计分**。不是惩罚，是这类条目本来就不构成发现 |

> 探测过程中产生大量 E0 是正常的。写进"自我否定清单"即可，不要塞进正式报告占位。

### 4.3 严重度（决定基数）

| 级别 | 判据 | 基数分 |
|---|---|---|
| **S1 阻断级** | 崩溃 / 数据损坏 / 任务文件写坏 / 命令注入 / 越权 / 凭证泄露 / 静默丢用户工作 | 10 |
| **S2 核心功能错误** | 工具返回错误结果、API 请求发错目标、上下文错乱导致模型行为异常、状态机跑飞 | 6 |
| **S3 边界退化** | 边界条件算错、错误路径不清理/不释放、提示缺失、轻微泄漏、UI 局部错位 | 3 |
| **S4 健壮性隐患** | 有风险但当前不可触发或影响极小 | 1 |

**虚报惩罚**：把低严重度报成高严重度，环节二未被证伪、但裁判复核为低严重度的，按**低严重度**计分，且该选手发掘分 **-3**/条。

### 4.4 单条 bug 的必填格式

```markdown
### [oc-003] 标题：一句话说清哪个输入导致哪种错误结果

- **严重度**：S2（理由：……）
- **证据等级**：E2（理由：已复现/仅静态推导/……）
- **位置**：`src/xxx/yyy.ts:412`（可多列，必须精确到行）
- **触发路径**：用户动作 → `entry()` (src/a.ts:10) → `handler()` (src/b.ts:88) → 出错点
- **现象**：预期 ……；实际 ……
- **影响**：对用户 / 对数据 / 对成本的具体后果
- **复现步骤**：1) … 2) … 3) …（E2/E3 必填）
- **复现命令与输出**：（E3 必填，贴真实输出，注明是否与 §3.3 基线做过差集）
- **修复方案**：改 `src/xxx/yyy.ts:412` 的 `<函数名>`，把 `<现有逻辑>` 改为 `<新逻辑>`；副作用注意 ……
- **上游对照**（选填，加分项）：claude-code 2.1.287 同位置是否已修？是/否/未查
```

ID 前缀：`claude-code` → `cc-`，`opencc` → `oc-`，`workbuddy` → `wb-`，`trae-code` → `tc-`。

### 4.5 结尾汇总表（裁判按这张表核对数量与去重）

| ID | 标题 | 严重度 | 证据等级 | 位置 |
|---|---|---|---|---|
| oc-001 | … | S2 | E3 | `src/x/y.ts:412` |

### 4.6 环节一质量红线

- 不得凑数：同一根因的多个表现算**一条**，不要拆成五条刷数量。
- 不得把"代码风格""命名不好""没有注释"当 bug。
- 不得把上游设计如此的行为当 bug（若你认为上游有改进空间，请放到"自我否定清单"并标注为改进建议）。
- **质量优先于数量**：10 条 E3 的价值远高于 50 条 E1。

## 5. 环节二 · 交叉评审

环节一收口后开放。你要读**另外三位**选手的 `bug-hunt-*.md`，逐一裁决。

### 5.1 交付物

`docs/bugs/bug-hunt-game-10-06/hunt-review-<你的名字>.md`，结构见 `TEMPLATE-hunt-review.md`。

### 5.2 裁决枚举（对他人每一条都判）

| 裁决 | 含义 | 你的理由必须包含 |
|---|---|---|
| `CONFIRMED` | 问题真实存在 | 你在源码里核到的 `file:line` + 成立的理由 |
| `PARTIAL` | 问题真实存在但作者说错了严重度/触发条件/影响范围 | 错在哪，作者的版本应该怎么改写 |
| `REJECTED` | 问题不存在或不构成缺陷 | **具体指出作者推理的哪一步断了**，不能只说"我看不出来" |
| `NOT-ENOUGH-EVIDENCE` | 可能真，但作者给的证据不足以支撑其严重度/触发条件 | 还缺什么证据才能成立 |
| `DUPLICATE` | 与另一位选手报告的是同一处 | 标注 `DUPLICATE-OF: <对方 ID>`；**双方都照常计分** |

> **关键：你的裁决必须落在源码上，不能只落在对方文档上。** 评审时至少要 `Read` 到每一处被引用的 `file:line`，确认行号所指的东西和作者描述的一致。这一条裁判会抽查（见 §6.2 评审分表"行号核实"）。

### 5.3 抽验要求（硬性）

对你判为 `CONFIRMED`/`REJECTED` 的条目，**至少抽 3 条**（跨不同选手、不同严重度）**亲手复验**：

- 复验方式不限（读源码追调用链 / 跑 `bun test <单个文件>` / 跑 `/tmp` 下的最小复现物）。
- 在报告里单列 `## 抽验记录` 一节，逐条写：我做了什么、看到了什么、结论是否与作者一致。

没做抽验直接照抄作者结论的，评审分大幅扣减。

### 5.4 主动新发现（硬性）

单列 `## 评审中额外发现` 一节：评审过程中你在源码里顺手抓到、但不在任何一份原报告里的问题。**至少 1 条**（真有就多写，没有就写"未发现额外问题"并列出你实际看过的地方）。

**这一节不是可选礼貌。** 它是对抗"读文档不读代码"最直接的检验手段：只会复读别人报告的人，这一节必然是空的。

### 5.5 评审质量红线

- 不得因为"我觉得不可能"就 `REJECTED`——必须指出推理断点。
- 不得把 `PARTIAL` 当 `REJECTED` 用来逃避思考。
- 误杀真 bug（裁判终裁为 `CONFIRMED` 而你判 `REJECTED`）是评审环节**最严重的错误**，单独扣分（§6.2）。

## 6. 环节三 · 裁判与排名

由裁判（Claude / zai）执行，产出 `docs/bugs/bug-hunt-game-10-06/VERDICT.md`。

### 6.1 裁判自查（裁判自己的纪律，先声明）

1. **每一条进入排名的 bug，我必须亲自打开 `file:line` 核对。** 选手写了不等于存在。
2. **文档写得详细不等于 bug 真实。** "证据看起来很硬"是我的主观印象，不能替代复核。
3. **我无法判定、需要完整 TUI 环境才能验证的**，标记为 `UNVERIFIED`，**不计入有效分**，并在 VERDICT 里公开列出是哪几条、为什么无法判定。
4. **我报告里的每一处行号引用都会自己再核一遍**，不复述选手的转述。
5. 裁判结果如有错判，选手可在环节三当场申辩，裁判复核后可修正并公开记录修正。

### 6.2 计分公式（满分 100）

**发掘分 60**

```
单条得分 = 严重度基数(S) × 证据系数(E)
严重度基数：S1=10, S2=6, S3=3, S4=1
证据系数：  E3=1.0, E2=0.8, E1=0.5, E0=0
同一条缺陷被多人发现：各人照常计分（不设唯一归属）
发掘分 = Σ(有效条目得分)，上限 60
```

量级参考（算式已展开，据此自测你的产出处在什么水位）：

| 典型产出 | 算式 | 发掘分 |
|---|---|---|
| 3 条 S2/E2 | 6×0.8 ×3 | 14.4 |
| 5 条 S2/E3 | 6×1.0 ×5 | 30 |
| 1×S1/E3 + 5×S2/E3 + 2×S3/E2 | 10 + 30 + 4.8 | 44.8 |
| 2×S1/E3 + 6×S2/E3 | 20 + 36 = 56 | 56 |
| 3×S1/E3 + 7×S2/E3 | 30 + 42 = 72 | 打满 60 |

额外扣分：
- 提交中 `E0` 占比 > 50%（正式报告区，不含自我否定清单）→ 记"低证据密度"，**评审分 -5**。
- 严重度虚报（§4.3）→ **-3/条**。
- 违规（§8）→ 见扣分表。

**评审分 40**

| 项 | 分值 | 规则 |
|---|---|---|
| 裁决正确率 | 20 | 每条 2 分；与裁判终裁不一致 **-2**；**误杀真 bug（真 CONFIRMED 被你判 REJECTED）额外 -1** |
| 抽验质量 | 12 | 抽验条目中"你的复验结论与事实一致"的比例 × 12；未做抽验直接给 0 |
| 主动新发现 | 8 | 按 `S×0.5` 计：S1=5, S2=3, S3=1.5, S4=0.5（以裁判复核为准） |
| 行号核实 | 扣分项 | 裁判抽查 3 条你的引用，核错一处 **-2** |

### 6.3 同分裁决

1. 有效 S1+S2 条数多者胜
2. 评审误判少者胜
3. 仍并列：裁判依证据组织质量主观判定，并在 VERDICT 中说明理由

## 8. 违规处理

| 违规 | 判定 | 处罚 |
|---|---|---|
| 修改 `src/` 等仓库既有文件 | `git status` 可查 | 该场次**发掘分清零**，直接出局 |
| `git commit` / `reset` / `stash` / 改 config | git 状态可查 | 同上，出局 |
| 环节一偷看他人 `bug-hunt-*.md` | 我会核对各文档的措辞与发现顺序是否异常雷同 | 发掘分 **-15**，并公开记录 |
| 删除 / 篡改他人文档 | 文件时间戳与内容 | **出局** |
| 编造证据（贴不存在的命令输出、伪造 `file:line`） | 我逐条复核输出 | 该条目作废；若 ≥2 条，直接**出局** |
| 跑全量 `bun test` | 耗时会体现 | 不扣分，但**报告中出现依赖全量跑的证据一律降为 E1** |

## 10. 给选手的临门一脚

这个仓库 75 万行，浅层 bug（少个 await、判空不全）早被上游和前几轮修补扫过大半。**真正值钱的 bug 在缝隙里**：

- 跨模块契约不一致（A 模块以为 B 返回 `undefined` 是正常，B 实际抛异常）
- 异步竞态与状态残留（`query.ts` / `QueryEngine` / 工具执行管线）
- 错误路径上的清理遗漏（`finally` 缺失、句柄/监听器/子进程泄漏）
- fork 特有改造的回归点：`src/mods/`（裸 `import()` 加载用户 JS）、`src/coordinator/`、`src/memdir/`、`src/upstreamproxy/`
- 特性开关组合下的行为分叉（`scripts/build.ts` 剥离 voice / proactive / kairos，非 ant 构建的 gate 行为）

**不要为了赢而堆 E0。** 一条被裁判亲自核实为真的 S2，比二十条看起来很专业的猜测值钱得多——而猜错还要倒扣。
