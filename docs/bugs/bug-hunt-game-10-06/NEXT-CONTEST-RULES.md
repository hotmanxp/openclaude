## 1. E3 拆成 E3a / E3b

### 本场暴露的问题

现有 E3 的定义是「测试必须真实执行被测模块，禁止用 `mock.module` 把被测对象本身替换掉」。这条**拦不住一类特殊的假证据**：

> 选手写了个脚本调 `transformModRenderText(H(text))`，观察到输出被套了两遍，于是宣称「渲染链被套两遍」。

脚本确实真实执行了真实模块——它满足现行 E3 的**字面要求**。但它证明的是「*函数被调用两次*会套两遍」，而缺陷需要证明的是「*React 树会对同一段文本调用两次*」。前者是恒真式，后者才是命题。

**我（裁判）也栽在同一个坑里**：把 workbuddy 的脚本判为「三重独立验证」，还给它标了全场最高分。三个「独立验证」全部在验证那个较弱命题。这是本场最贵的错误。

### 改法

| 等级 | 含义 |
|---|---|
| **E3a** | 真实执行了被测模块，证明了**模块自身**的行为 |
| **E3b** | 真实执行了被测模块**在其真实调用方之中**的行为——组件层缺陷（UI、渲染、事件流）必须达到 E3b，即**实际渲染/触发那条路径**并断言可观测结果（handler 调用次数、DOM/输出内容） |

组件层缺陷若只达到 E3a，**按 E2 计分**。

### 落地

- 裁判在 §4.2 判定时明确标注 E3a / E3b，不允许只写「E3」
- 本场补一句提示：组件层要达到 E3b 需要渲染组件树，这是可做到的（本场修 cc-011 时就用真实 socket + 真实模块证明了），只是**没人做**

## 2. 探针必须自带**有效的**对照组

### 本场暴露的问题

对照组失效在本场出现两次，一次是选手的，一次是我的。

**选手侧**：wb-r01 的脚本最后一段号称用 `toUpperCase` 做幂等对照，实际输出仍是第一个 wrapper mod 的结果——`renderTap` 的模块级 LRU 让 `cache.get('hello')` 命中了前一段的陈旧条目，**那段「对照」什么都没对照**。

**裁判侧**（更糟）：我判这个对照「失效但结论正确」，理由是修正版脚本证明了结论。**修正版同样只验证了较弱命题**——即提案 1 说的那个问题。两个层次的错误叠在一起，才让一个假发现拿了全场最高分。

### 改法

- 每条 E3 复现物必须含**对照组**，且对照组要证明**「如果没有这个 bug，输出会不同」**
- 对照组本身**先跑一遍、贴输出**——如果对照组的输出与实验组相同，它就没有区分力，等于没做
- 探针使用模块级缓存 / 单例 / 全局状态时，**每次对照前必须显式复位**，并在脚本里说明复位的调用

这一条对裁判同样适用：**裁判的复核脚本也要有对照组**。本场我给选手的复核意见里没有这一条，是规则的漏洞。

## 3. 证据必须注明**在哪个运行时下执行**

### 本场暴露的问题

oc-002（`/mods reload` 不加载新代码）的修复是给 import specifier 加一个 `?openccReload=N` 查询串。这个修法在 **Node 下生效，在 Bun 下无效**——Bun 的 ESM loader 忽略 file: URL 上的 query。

后果是：**任何用 `bun test` 写的回归测试都观察不到修复前后的差异**，会给假绿。本仓库用 Bun 做测试工具链，而运行时是 Node，两者对同一个修复的表现不同。

这不是选手的疏忽——按现行规则，`bun test` 通过就是 E3，谁也不会去怀疑运行时差异。

### 改法

- 复现物必须注明执行环境：`运行时: Node vX / bun vX`，并说明**为什么这个环境能代表用户**
- 若修复的效果依赖运行时，复现脚本**必须用产品运行时跑**，并在头部注明
- 裁判复核时，若某条 E3 的结论只在非产品运行时下成立，降级为 E2

> 本场补充：这条不只是「证据格式」问题。它揭示了更一般的形态——**测试工具链与产品运行时不一致，本身就是一类系统性证据风险**。凡是「修复只在某一运行时下可见」的缺陷，都应要求双运行时验证。

## 4. 修复阶段与裁定阶段分离，新证据可回溯改判

### 本场暴露的问题

本场在**修复阶段**发现了三处裁定阶段的问题：

- **wb-r01**：裁定 CONFIRMED + 全场最高分，修复阶段复核后推翻，需撤销 3.0 分并下调选手总分
- **oc-002**：修复代码因与另一会话的 WIP 同文件，被裹进了一个无关的 feature commit，**git 历史把它归错了地方**
- **cc-010**：申辩阶段翻案（S2/E3），但这已经是现有流程覆盖的

现行流程里，裁判改判只在**申辩环节**有正式通道。修复阶段发现新证据，没有对应的记录方式，最后只能靠在 `plan.md` 里手写勘误段——容易漏，且不影响任何正式文档的分数口径。

### 改法

- 增加一个**正式的「勘误」环节**，位于修复阶段之后
- 勘误必须写明：原判 → 新判 → 触发新证据的那次复核 → **分数与排名的连带影响**
- 勘误**必须同步更新**公告的分数表，而不是只在附录里加一段——本场 wb-r01 的勘误就差点只改了 `VERDICT.md` 而漏了 `ANNOUNCEMENT.md` 的排名表
- 代码修复若因外部原因（并发工作、文件冲突）无法独立提交，须**记录归属**，避免日后按 commit 追溯时找不到

## 5. 「不可触发」必须自证

### 本场暴露的问题

oc-007（`monitor_mcp` 详情面板空白）与 wb-004（`permissionDenials` 跨 turn 不重置）在裁定阶段被判为「潜伏缺陷」，理由分别是「全仓无创建点」和「生产入口每次新建」。

这两条**机制成立、当前不可触发**。但「全仓无创建点」这个断言本身是**负向断言**——grep 不到不等于不存在，可能经过字符串拼接、动态注册或外部输入构造。要作为定级依据，就需要自证。

本场两条恰好都验证到位了（grep 到只有类型定义和谓词；两个 `new QueryEngine` 都在函数内每次新建），所以归档是安全的。但**规则没有要求这一步**，下次不一定这么走运。

### 改法

- 声称「当前不可触发」的条目，必须附**不可触发的依据**（全仓搜索范围、构造点的枚举、或一个能覆盖未来创建的守卫测试）
- 无法自证的，按 **E1** 计（机制成立但触发性未证），不按 E2/E3
- 裁判复核「不可触发」时，需独立重跑该搜索，而不是接受选手的结论

## 附：本场三条「我判错」的记录，作为反面教材

规则提案若无反面教材，很容易被当成「吹毛求疵」。本场裁判（也就是我）错了三次：

| 条目 | 我怎么错的 | 违反了本提案的哪条 |
|---|---|---|
| **wb-r01** | 判 CONFIRMED +「三重独立验证」+ 全场最高分，实际验证的是较弱命题 | 提案 1、2 |
| **cc-006** | 探针自己骗自己（把不可达路径当成真实路径），中间还因 fixture 本身是被上游脱敏的 token 而误判修复无效 | 提案 2 |
| **oc-010** | 写了个「更严谨」的守卫，模拟后发现**比原代码更差**，差点把正确代码改坏 | ——（这条不是规则问题，是「改代码前先建模验证」） |

第三条与前两条性质不同，但它指向一个同样值得写进流程的习惯：**先写复现脚本，再改代码**。本场 oc-010 如果没有先建模，我大概已经把一个 bug 修成了另一个 bug。
