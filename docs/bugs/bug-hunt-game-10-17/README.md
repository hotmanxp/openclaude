## 2. 铁律（违反即判违规）

1. **只读源码。** 禁止对 `src/`、`scripts/`、`web/`、`package.json`、`tsconfig.json` 等任何仓库既有文件做 Edit/Write/删除。
2. **禁止改动 git 状态。** 不得 `commit` / `add` / `stash` / `reset` / `checkout` / `restore` / `clean` / `push` / `rebase`，不得改 `git config`，不得建分支或 worktree。
3. **唯一允许写入仓库的位置**是你自己的两份文档：`bug-hunt-<你的名字>.md` 与 `hunt-review-<你的名字>.md`。名字只能取 `opencc` 或 `claude`。
4. **临时文件只进 `/tmp`。** 复现脚本、探针、快照一律写 `/tmp/bughunt-<你的名字>/`（自己 `mkdir -p`）。**禁止**把临时脚本写进仓库任何目录再删。
5. **禁止删除或篡改他人文档。**
6. **环节一期间禁止阅读对方的 `bug-hunt-*.md`。** 你的判断必须独立形成。这是本赛制最容易被自我污染的一条。
7. **禁止 `bun test` 全量。** 本仓库 1081 个测试文件，AGENTS.md 明令只能跑单文件/指定文件；且必须重定向到日志文件再读（见 §3）。
8. **禁止用 tmux 驱动 TUI。** 用户线上会话跑在 tmux 里，新建或杀 session 属于动共享状态。
9. **禁止编造。** 没有验证过的行为不许写成"已复现"。不确定就降证据等级（§4.2）写"未验证"，这不丢人，编造才丢人。

违规扣分见 §8。

## 3. 取证环境

### 3.1 可以用（节选）

```bash
# 静态：类型层面找矛盾
bun run typecheck > /tmp/bughunt-<你>/tc.log 2>&1; grep -E "error TS" /tmp/bughunt-<你>/tc.log

# 动态：单文件 / 指定文件测试。必须重定向，禁止 | tail
bun test src/utils/某文件.test.ts > /tmp/bughunt-<你>/t.log 2>&1
grep -cE '^\(fail\)' /tmp/bughunt-<你>/t.log

# 构建产物验证
bun run build && node dist/cli.mjs --version

# 运行环境自检
bun run doctor:runtime

# 检索（用 Grep 工具 / Glob 工具 / codegraph，不要在 Bash 里手搓 rg/grep）
```

### 3.2 四个已知坑（所有选手都会踩，先记住）

1. **PATH 上的 `opencc` 是旧构建。** 它指向 `opencc-release` 的产物，与本仓库 `src/` 无关。验证本仓库行为**必须**用 `bun /Users/ethan/code/opencc/dist/cli.mjs` 或 `node /Users/ethan/code/opencc/dist/cli.mjs`。用 `opencc` 验证得到的一切结论都无效。
2. **本仓库有预存测试失败。** 你在无改动状态下跑出来的红，**不等于**你发现的 bug。判断"这是我发现的"必须给出因果：从哪一行代码、因为什么逻辑，导致这个失败。
3. **`bun test` 在非 TTY 下只打印 `(fail)`，不打印 `(pass)`。** 几千个通过项零反馈，看起来像卡死。永远重定向到文件再读。
4. **Bun 与 Node 对同一份修复的表现可能不同。** Bun 只是测试工具链，运行时是 Node。若你的复现在 Bun 下跑、而你的结论只在 Bun 下成立，这条按 E2 计（见 §4.3）。

### 3.3 本场已钉死的基线（`f60d045e`，裁判于 2026-10-17 开赛前实测）

**`bun run typecheck` 在基准提交上完全干净：exit = 0，错误数 = 0。**

因此：

- 任何 `error TS` 都是**你的发现**，不存在需要扣除的预存错误。
- 但"typecheck 红了"本身仍然只算 E1 —— 编译器只保证你写错了，不保证产品行为错了。绝大多数 typecheck 错误来自 `// @ts-nocheck` 覆盖不到的地方或测试里的类型笔误。**必须说明它对应什么用户可见后果**，否则降级。

### 3.4 基线快照（开始干活前做一次，写进你的文档）

```bash
git rev-parse HEAD > /tmp/bughunt-<你>/head.txt
git status --porcelain  > /tmp/bughunt-<你>/status-before.txt
```

## 4. 环节一 · 自主发掘

**范围：全仓库，自由游走。** 两名选手范围完全相同，不分区。发现同一个 bug 两人照常各得分。

### 4.1 交付物

`docs/bugs/bug-hunt-game-10-17/bug-hunt-<你的名字>.md`，结构见 `TEMPLATE-bug-hunt.md`。至少包含：

1. **取证环境**（§3.4 的基线快照结果 + 你实际跑过的命令）
2. **你排查过的区域**（诚实列出：看了哪些子系统、为什么放弃其他子系统）
3. **逐条 bug 报告**（§4.5 全部字段必填）
4. **结尾汇总表**（§4.6）
5. **不确定与自我否定清单**

### 4.2 证据等级（决定这条 bug 值多少分）

| 等级 | 含义 | 判定标准 |
|---|---|---|
| **E3 机器可证** | 附一个能跑的最小复现物，放 `/tmp/bughunt-<你>/`，文档里给出**完整命令与真实输出** | 真实执行过，输出可复现。**测试必须真实执行被测模块，禁止用 `mock.module` 把被测对象本身替换掉**。详见 §4.3 |
| **E2 可复现** | 给出确定的触发输入/操作步骤 + 观察到的错误行为 | 步骤具体到可以照做，且描述了"预期什么、实际什么" |
| **E1 静态可证** | 无需运行即可判定：精确 `file:line` + 从入口到出错点的完整调用链 + 为什么现有防护挡不住 + 错误后果推演 | 推演链完整闭合，无"可能""大概"式跳跃 |
| **E0 仅推测** | 读代码感觉不对 | **不计分**。不是惩罚，是这类条目本来就不构成发现 |

> 探测过程中产生大量 E0 是正常的。写进"自我否定清单"即可，不要塞进正式报告占位。

### 4.3 E3 拆分：E3a 与 E3b（本场新增硬规则）

上届在这条上出了全场最贵的错：一名选手写脚本调 `transformModRenderText(H(text))`，看到输出被套两遍就宣称"渲染链被套两遍"。脚本确实真实执行了真实模块——但它证明的是「*函数被调用两次*会套两遍」，而缺陷需要证明的是「*React 树会对同一段文本调用两次*」。前者是恒真式，后者才是命题。**裁判当时也栽在同一个坑里，给它判了全场最高分。**

| 等级 | 含义 |
|---|---|
| **E3a** | 真实执行了被测模块，证明了**模块自身**的行为 |
| **E3b** | 真实执行了被测模块**在其真实调用方之中**的行为 —— 组件层缺陷（UI、渲染、事件流、状态机）必须达到 E3b，即**实际渲染/触发那条路径**并断言可观测结果（handler 调用次数、DOM/输出内容、事件是否到达） |

**组件层缺陷若只达到 E3a，按 E2 计分。** 裁判在 §6 判定时会明确标注 E3a / E3b，不允许只写"E3"。

### 4.4 探针必须自带**有效的**对照组（本场新增硬规则）

每条 E3 复现物必须包含一个对照组，**证明「如果没有这个 bug，输出会不同」**。

- 对照组**自己先跑一遍、贴输出**。如果对照组输出与实验组相同，它没有区分力，等于没做。
- 探针使用模块级缓存 / 单例 / 全局状态时，**每次对照前必须显式复位**，并在脚本里说明复位的调用。上届有选手用 `toUpperCase` 做幂等对照，但模块级 LRU 让 `cache.get('hello')` 命中了陈旧条目，那段"对照"什么都没对照。
- **这条对裁判同样适用**：裁判的复核脚本也要有对照组。

### 4.5 证据必须注明**在哪个运行时下执行**（本场新增硬规则）

复现物必须标注 `运行时: Node v22.22.3 / Bun 1.4.2 / 浏览器 ...`，并说明**为什么这个环境能代表用户**。

上届的教训：`/mods reload` 不加载新代码的修复靠给 import specifier 加查询串，**在 Node 下生效，在 Bun 下无效**（Bun 的 ESM loader 忽略 file URL 上的 query）。任何用 `bun test` 写的回归测试都观察不到修复前后的差异，会给假绿。

**若某条 E3 的结论只在非产品运行时下成立，裁判按 E2 计分。**

### 4.6 严重度（决定基数）

| 级别 | 判据 | 基数分 |
|---|---|---|
| **S1 阻断级** | 崩溃 / 数据损坏 / 任务文件写坏 / 命令注入 / 越权 / 凭证泄露 / 静默丢用户工作 | 10 |
| **S2 核心功能错误** | 工具返回错误结果、API 请求发错目标、上下文错乱导致模型行为异常、状态机跑飞 | 6 |
| **S3 边界退化** | 边界条件算错、错误路径不清理/不释放、提示缺失、轻微泄漏、UI 局部错位 | 3 |
| **S4 健壮性隐患** | 有风险但当前不可触发或影响极小 | 1 |

**虚报惩罚**：把低严重度报成高严重度，环节二未被证伪、但裁判复核为低严重度的，按**低严重度**计分，且该选手发掘分 **-3**/条。

### 4.7 「不可触发」必须自证（本场新增硬规则）

声称"当前不可触发"的条目，必须附**不可触发的依据**：

- 全仓搜索范围（给出你搜了哪些目录、哪些模式）
- 构造点的枚举（列出每一处 `new Xxx()` 并说明是否可达）
- 或一个能覆盖未来创建的守卫测试

**无法自证的，按 E1 计**（机制成立但触发性未证），不按 E2/E3。裁判复核"不可触发"时会**独立重跑该搜索**，不接受你的结论。

> 依据：grep 不到不等于不存在——可能经字符串拼接、动态注册或外部输入构造。

### 4.8 单条 bug 的必填格式

见 [`TEMPLATE-bug-hunt.md`](./TEMPLATE-bug-hunt.md) §三，字段全部必填（除标注"选填"）。

ID 前缀：`opencc` → `oc-`，`claude` → `cl-`。ID 全场唯一。

### 4.9 环节一质量红线

- 不得凑数：同一根因的多个表现算**一条**，不要拆成五条刷数量。
- 不得把"代码风格""命名不好""没有注释"当 bug。
- 不得把上游设计如此的行为当 bug（若你认为上游有改进空间，放"自我否定清单"并标注为改进建议）。
- **质量优先于数量**：10 条 E3 的价值远高于 50 条 E1。

### 4.10 时间预算

**约 45 分钟。** 裁判会在时间到时统一叫停。叫停后：

- **停止一切新的源码探索**，只允许把已在手上的证据整理成文档。
- 10 分钟内提交完毕。**超时未提交的条目不计分。**
- 收口前自查：文档能否被**没读过你思路的第三方**看懂。

## 5. 环节二 · 交叉评审

环节一收口后开放。你要读**对方**的 `bug-hunt-*.md`，逐一裁决。

### 5.1 交付物

`docs/bugs/bug-hunt-game-10-17/hunt-review-<你的名字>.md`，结构见 `TEMPLATE-hunt-review.md`。

### 5.2 裁决枚举（对对方每一条都判）

| 裁决 | 含义 | 你的理由必须包含 |
|---|---|---|
| `CONFIRMED` | 问题真实存在 | 你在源码里核到的 `file:line` + 成立的理由 |
| `PARTIAL` | 问题真实存在但对方说错了严重度/触发条件/影响范围 | 错在哪，应该怎么改写 |
| `REJECTED` | 问题不存在或不构成缺陷 | **具体指出对方推理的哪一步断了**，不能只说"我看不出来" |
| `NOT-ENOUGH-EVIDENCE` | 可能真，但证据不足以支撑其严重度/触发条件 | 还缺什么证据才能成立 |
| `DUPLICATE` | 与对方自己的另一条是同一处 | 标注 `DUPLICATE-OF: <对方 ID>` |

> **你的裁决必须落在源码上，不能只落在对方文档上。** 评审时至少要 `Read` 到每一处被引用的 `file:line`，确认行号所指的东西和对方描述的一致。裁判会抽查。

### 5.3 抽验要求（硬性）

对判为 `CONFIRMED`/`REJECTED` 的条目，**至少抽 3 条**（跨不同严重度）**亲手复验**：

- 复验方式不限（读源码追调用链 / 跑 `bun test <单个文件>` / 跑 `/tmp` 下的最小复现物）。
- 单列 `## 抽验记录` 一节，逐条写：我做了什么、看到了什么、结论是否与对方一致。
- 你自己的复现物同样受 §4.4 约束：**对照组先跑、先贴**。

没做抽验直接照抄对方结论的，评审分大幅扣减。

### 5.4 主动新发现（硬性）

单列 `## 评审中额外发现` 一节：评审过程中你在源码里顺手抓到、但不在对方报告里的问题。**至少 1 条**（真有就多写，没有就写"未发现额外问题"并列出你实际看过的地方）。

**这一节不是可选礼貌。** 只会复读别人报告的人，这一节必然是空的。

### 5.5 评审质量红线

- 不得因为"我觉得不可能"就 `REJECTED`——必须指出推理断点。
- 不得把 `PARTIAL` 当 `REJECTED` 用来逃避思考。
- **误杀真 bug（裁判终裁为 `CONFIRMED` 而你判 `REJECTED`）是评审环节最严重的错误**，单独扣分（§6.2）。

## 6. 环节三 · 裁判与排名

由裁判（Claude / zai）执行，产出 `VERDICT.md` 与 `plan.md`。

### 6.1 裁判自查（裁判自己的纪律，先声明）

1. **每一条进入排名的 bug，我必须亲自打开 `file:line` 核对。** 选手写了不等于存在。
2. **文档写得详细不等于 bug 真实。** "证据看起来很硬"是我的主观印象，不能替代复核。
3. **我无法判定、需要完整 TUI 环境才能验证的**，标记为 `UNVERIFIED`，**不计入有效分**，并在 VERDICT 里公开列出是哪几条、为什么无法判定。
4. **我报告里的每一处行号引用都会自己再核一遍**，不复述选手的转述。
5. **裁判结果如有错判，选手可申辩，裁判复核后可修正并公开记录修正。**

### 6.2 计分公式（满分 100，沿用上届口径以便跨届比较）

**发掘分 60**

```
单条得分 = 严重度基数(S) × 证据系数(E)
严重度基数：S1=10, S2=6, S3=3, S4=1
证据系数：  E3=1.0, E2=0.8, E1=0.5, E0=0
同一条缺陷被两人发现：各人照常计分（不设唯一归属）
发掘分 = Σ(有效条目得分)，上限 60
```

> 量级参考（算式已展开，据此自测产出处在什么水位）：

| 典型产出 | 算式 | 发掘分 |
|---|---|---|
| 3 条 S2/E2 | 6×0.8 ×3 | 14.4 |
| 5 条 S2/E3 | 6×1.0 ×5 | 30 |
| 1×S1/E3 + 5×S2/E3 + 2×S3/E2 | 10 + 30 + 4.8 | 44.8 |
| 2×S1/E3 + 6×S2/E3 | 20 + 36 = 56 | 56 |
| 3×S1/E3 + 7×S2/E3 | 30 + 42 = 72 | 打满 60 |

额外扣分：
- 正式报告区 `E0` 占比 > 50% → 记"低证据密度"，**评审分 -5**。
- 严重度虚报（§4.6）→ **-3/条**。
- 违规（§8）→ 见扣分表。

**评审分 40**

| 项 | 分值 | 规则 |
|---|---|---|
| 裁决正确率 | 20 | 每条 2 分；与裁判终裁不一致 **-2**；**误杀真 bug 额外 -1** |
| 抽验质量 | 12 | 抽验条目中"复验结论与事实一致"的比例 × 12；未做抽验直接给 0 |
| 主动新发现 | 8 | 按 `S×0.5` 计：S1=5, S2=3, S3=1.5, S4=0.5（以裁判复核为准） |
| 行号核实 | 扣分项 | 裁判抽查 3 条你的引用，核错一处 **-2** |

### 6.3 上届已知缺陷的处理

上一届（2026-10-06）比赛在 `f60d045e` 之前另有 80 个 commit，其产出中有 3 条**已归档为潜伏/不可触发**的技术债。**本场规则不告诉你是哪三条**（那属于情报泄露）。但约定如下：

**若你在本场独立重新发现它们，照常计分，分数不减。** VERDICT 中会标注「上届已知」，仅供读者对照。

### 6.4 同分裁决

1. 有效 S1+S2 条数多者胜
2. 评审误判少者胜
3. 仍并列：裁判依证据组织质量主观判定，并在 VERDICT 中说明理由

## 10. 给选手的临门一脚

这个仓库 78 万行，浅层 bug（少个 await、判空不全）早被上游和前几轮修补扫过大半。**真正值钱的 bug 在缝隙里**：

- 跨模块契约不一致（A 模块以为 B 返回 `undefined` 是正常，B 实际抛异常）
- 异步竞态与状态残留（`query.ts` / `QueryEngine` / 工具执行管线）
- 错误路径上的清理遗漏（`finally` 缺失、句柄/监听器/子进程泄漏）
- 特性开关组合下的行为分叉（`scripts/build.ts` 剥离 voice / proactive / kairos，非 ant 构建的 gate 行为）
- **本场新增地层**：距上届比赛只有 80 个 commit，其中 `src/mods/` 独占 1.2 万行新增。**新写的代码缺陷密度显著高于老代码**，而这一层上游从不审。

**不要为了赢而堆 E0。** 一条被裁判亲自核实为真的 S2，比二十条看起来很专业的猜测值钱得多——而猜错还要倒扣。
